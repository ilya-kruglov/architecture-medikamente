# Аналитический слой с учётом Privacy by Design

## Контекст
Компания планирует использовать накопленные данные для BI-отчётов, обучения ML-моделей и создания AI-сервисов. При этом важно, чтобы аналитики и дата-сайентисты не имели доступа к сырым PII и медицинским данным в явном виде. Это требование закреплено в 152-ФЗ и является частью стратегии Privacy by Design.

## Архитектура аналитического слоя

        ▲                        ▲                        ▲
        │                        │                        │

## Принципы обработки

1. **Data Minimization** – в аналитический слой передаются только те поля, которые действительно необходимы для анализа. Избыточные поля (например, точный адрес, номер телефона) исключаются.

2. **De‑identification** – все прямые идентификаторы (ФИО, телефон, email, СНИЛС) удаляются или заменяются на псевдонимы (токенизация). Косвенные идентификаторы (возраст, пол, район проживания) агрегируются до уровней, исключающих реидентификацию.

3. **k‑Anonymity** – для табличных данных обеспечивается, что каждая запись неотличима от как минимум `k-1` других записей по квази-идентификаторам.

4. **Дифференциальная приватность** – при построении агрегатов и обучении моделей добавляется шум, гарантирующий, что результат не позволяет определить, участвовал ли конкретный пациент в наборе данных.

5. **Разделение доступа** – аналитики не имеют доступа к операционной базе. Все запросы выполняются только к обезличенному Data Lake. Права доступа к зонам Data Lake разграничены (только чтение для аналитиков, запись – только для пайплайнов).

6. **Аудит** – все запросы к Data Lake логируются и могут быть проверены на предмет наличия попыток реидентификации.

## Технологический стек для аналитического слоя

| Компонент | Технология | Назначение |
|-----------|------------|------------|
| Ингейшн | Apache Kafka / NiFi | Сбор данных из операционных систем |
| Обработка (Anonymization) | Apache Spark / Python (Pandas) | Обезличивание, трансформация |
| Хранилище | ClickHouse (для агрегатов) / HDFS (для сырых данных) | Скалярное и файловое хранение |
| Доступ к данным | Trino (Presto) / Spark SQL | Запросы к Data Lake |
| Визуализация | Superset / Tableau / FineBI | BI-отчёты |
| ML/AI | Jupyter / MLflow / PyTorch | Обучение моделей на обезличенных данных |

## Поток данных (пример)

1. **Событие:** пациент совершает оплату.
2. **Операционная БД** сохраняет запись с ПДн/PII.
3. **Асинхронный пайплайн** (Kafka) забирает событие и передаёт в **Anonymization Service**.
4. **Anonymization Service** выполняет:
   - Удаление ФИО, телефона, email.
   - Замену ID пациента на суррогатный ключ (не связываемый с оригиналом).
   - Агрегацию возраста до диапазона (например, 25-34).
   - Удаление точного адреса, оставление только района (если необходимо).
   - Применение k‑анонимности к группе записей (k=20).
5. **Обезличенные данные** записываются в **Clean zone** Data Lake.
6. **Аналитик** строит отчёт по обезличенным данным, не имея доступа к исходным ПДн/PII.
7. **При необходимости** дата-сайентист обучает модель на данных из Curated zone (уже с готовыми признаками), соблюдая дифференциальную приватность.

## Гарантии соответствия 152-ФЗ
- Все операции с ПДн/PII (до обезличивания) остаются в защищённом контуре (операционная БД с шифрованием и строгим доступом).
- Data Lake не содержит прямых идентификаторов, что снижает требования к защите (согласно закону, обезличенные данные не являются ПДн).
- Все процессы аудируются: есть логи того, когда и какие данные были обезличены и кем использовались.

## Заключение
Предложенный аналитический слой полностью соответствует принципам Privacy by Design, позволяя компании извлекать ценность из данных без риска нарушения приватности пациентов.
