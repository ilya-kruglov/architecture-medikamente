# Cutover-план миграции (Parallel run)

## Общая структура этапов

| Этап | Название | Длительность | Основная цель |
|------|----------|--------------|---------------|
| 0 | Подготовка и инфраструктура | 2 недели | Развернуть целевую инфраструктуру, настроить CI/CD, обеспечить безопасность |
| 1 | Разработка ETL и миграция данных | 2 недели | Очистить, классифицировать, зашифровать и перенести данные в новую БД |
| 2 | Параллельный запуск (Shadow mode) | 3 недели | Запустить новую систему в режиме "только чтение", сверять данные с легаси |
| 3 | Переключение (Cutover weekend) | 3 дня | Остановить старую систему, мигрировать дельту, включить запись в новой |
| 4 | Мониторинг и стабилизация | 2 недели | Наблюдение за производительностью, устранение инцидентов |
| 5 | Вывод из эксплуатации (Decommission) | 1 неделя | Архивация старой системы, отключение оборудования |

---

## Детальный план по этапам

### Этап 0: Подготовка и инфраструктура (День 1–14)

| Действие | Ключевые задачи | Ответственные | Сроки | Риски / Меры |
|----------|-----------------|---------------|-------|--------------|
| Развернуть Kubernetes-кластер | Установка и настройка K8s, настройка сетевых политик, установка Istio | DevOps, Tech Lead | День 1–5 | *Риск: ошибки конфигурации.* Мера: предварительное тестирование в staging-окружении |
| Настроить CI/CD | GitLab CI / GitHub Actions, автоматическая сборка, тестирование, деплой | DevOps | День 3–7 | *Риск: неправильные артефакты.* Мера: проверка сборки на тестовом кластере |
| Развернуть IAM (Keycloak) | Настройка интеграции с AD, MFA, создание ролей | Tech Lead, DevOps | День 6–10 | *Риск: сбой аутентификации.* Мера: резервное копирование конфигурации |
| Развернуть шифрование (Vault) | Установка Vault, инициализация ключей, настройка политик | DevOps, Security | День 8–12 | *Риск: потеря мастер-ключа.* Мера: HSM для мастер-ключа, офлайн-бэкап |
| Настроить мониторинг и аудит | Prometheus, Grafana, ELK, Wazuh | DevOps, Business Analyst | День 10–14 | *Риск: пропуск алертов.* Мера: тестовые алерты перед запуском |

### Этап 1: Разработка ETL и миграция данных (День 15–28)

| Действие | Ключевые задачи | Ответственные | Сроки | Риски / Меры |
|----------|-----------------|---------------|-------|--------------|
| Анализ и очистка данных | Инвентаризация Excel-файлов, выявление дублей, невалидных записей | Business Analyst, DBA | День 15–20 | *Риск: потеря данных.* Мера: полный бэкап всех исходных файлов перед очисткой |
| Разработка ETL-пайплайна | Настройка Apache NiFi / Kafka для загрузки данных из Excel/1С в PostgreSQL | Data Engineer, Backend Dev | День 18–25 | *Риск: несоответствие схем.* Мера: валидация через JSON Schema перед загрузкой |
| Классификация и тегирование | Применение тегов (PII, Medical, Financial) к данным в новой БД | Data Engineer, Security | День 22–26 | *Риск: неправильная классификация.* Мера: ручная проверка выборки DPO |
| Шифрование данных | Шифрование столбцов с PII и Medical через pgcrypto, настройка Vault | DevOps, Backend Dev | День 24–28 | *Риск: потеря ключей.* Мера: тестовое дешифрование после каждого шага |

### Этап 2: Параллельный запуск (Shadow mode) (День 29–49)

| Действие | Ключевые задачи | Ответственные | Сроки | Риски / Меры |
|----------|-----------------|---------------|-------|--------------|
| Деплой новой системы (read‑only) | Развернуть микросервисы в режиме только чтения, подключить к БД | DevOps, Backend Dev | День 29–31 | *Риск: проблемы с подключением.* Мера: предварительный health‑check |
| Синхронизация данных в реальном времени | Настроить CDC (Debezium) с Excel/1С на новую БД (односторонняя) | Data Engineer | День 30–35 | *Риск: задержка синхронизации.* Мера: мониторинг лагов, алерты при >5 мин |
| Обучение и UAT (User Acceptance Testing) | Проведение тренингов для сотрудников (ресепшен, врачи, кассиры), сбор обратной связи | Business Analyst, Product Manager | День 32–42 | *Риск: сопротивление пользователей.* Мера: демонстрация преимуществ, супервайзеры на местах |
| Сверка данных (Reconciliation) | Ежедневное сравнение итоговых сумм, количества записей между старой и новой системой | Business Analyst, QA | День 35–49 | *Риск: расхождение данных.* Мера: создание скриптов для выявления расхождений, ручная проверка |
| Нагрузочное тестирование | Имитация пиковой нагрузки (запись 1000 пациентов/день) | QA, DevOps | День 40–45 | *Риск: падение производительности.* Мера: автоскейлинг, оптимизация запросов |

### Этап 3: Переключение (Cutover weekend) (День 50–52)

| Действие | Ключевые задачи | Ответственные | Сроки | Риски / Меры |
|----------|-----------------|---------------|-------|--------------|
| **Пятница 18:00** – Остановка операций в старой системе | Оповещение всех сотрудников, блокировка записи в Excel/1С | Project Manager, Business Analyst | Пятница, 18:00 | *Риск: незавершённые операции.* Мера: завершить все транзакции до остановки |
| **Пятница 18:30** – Миграция дельты | Перенос изменений, сделанных за последние 24 часа, в новую БД | Data Engineer | Пятница, 18:30–21:00 | *Риск: конфликт версий.* Мера: скрипты разрешения конфликтов (последняя запись побеждает) |
| **Пятница 21:00** – Включение записи в новой системе | Переключение микросервисов в режим read‑write, активация API Gateway | DevOps | Пятница, 21:00 | *Риск: ошибка конфигурации.* Мера: предварительное тестирование переключения на staging |
| **Суббота 08:00** – Начало работы по новой системе | Персонал работает в новой системе, старая система доступна только для чтения (аварийный режим) | Все сотрудники | Суббота, 08:00 | *Риск: массовые сбои.* Мера: служба поддержки на месте (tech lead + devops) |
| **Воскресенье 18:00** – Стабилизация | Все критические баги исправлены, система работает стабильно | Команда разработки | Воскресенье, 18:00 | *Риск: неисправленные баги.* Мера: hotfix-процедура, возможность отката на старую систему |
| **Понедельник 09:00** – Официальный запуск | Старая система переведена в режим "только для отчётов" (read-only) | DevOps | Понедельник, 09:00 | *Риск: нагрузка.* Мера: мониторинг ресурсов, алерты |
