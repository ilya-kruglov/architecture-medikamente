# Обоснование стратегии миграции

## 1. Контекст

Текущее состояние (As-Is):
- Файловый монолит: Excel-файлы как база данных, сканы PDF/JPG.
- 1С:Бухгалтерия и 1С:Торговля и склад в файловом режиме.
- Интеграции через OLE (устаревшая технология, без шифрования).
- Отсутствие контроля доступа, аудита, шифрования.
- Критические данные: ПДн/PII, медицинская тайна, финансовые операции.

Целевое состояние (To-Be):
- Микросервисная архитектура (Java, Kubernetes, PostgreSQL, ClickHouse).
- API Gateway, IAM (Keycloak), Policy Engine (OPA).
- Шифрование at rest и in transit, тегирование, аудит.
- Масштабируемость на 5x рост.

Бизнес-ограничения:
- Работа клиники не может быть остановлена на длительный срок.
- Ошибки в финансовых и медицинских данных недопустимы.
- Требуется строгое соответствие 152-ФЗ.

## 2. Сравнение стратегий миграции

| Критерий | High-level design | Parallel run | Branch by abstraction |
|----------|-------------------|--------------|------------------------|
| **Описание** | Разработка архитектуры "с нуля" и одномоментный переход (Big Bang) | Запуск старой и новой систем параллельно, постепенное переключение нагрузки | Постепенная замена функциональности через абстракции внутри кодовой базы |
| **Преимущества** | Единая архитектура, минимум промежуточных состояний | Минимальный риск для бизнеса, возможность отката в любой момент | Инкрементальный подход, непрерывная доставка |
| **Недостатки** | Высокий риск сбоя, сложность отката, длительный downtime | Высокие затраты на инфраструктуру (2 системы), сложность синхронизации данных | Требует высокого качества кода, не применим к файловым и 1С-системам |
| **Применимость к "Медикаменте"** | ❌ Недопустим – один сбой остановит клинику | ✅ Оптимален – безопасность и контролируемый переход | ❌ Невозможен – 1С и Excel не позволяют вводить абстракции |

## 3. Выбор стратегии: Parallel run

**Обоснование:**

1. **Минимизация рисков.** В сфере медицины и финансов ошибки недопустимы. Parallel run позволяет запустить новую систему "в тени" старой, сверять результаты и накопить уверенность перед переключением.
2. **Возможность отката.** На любом этапе, если новая система показывает сбои, нагрузка остаётся на старой системе.
3. **Обучение персонала.** Сотрудники могут осваивать новый интерфейс в режиме "только чтение" или на тестовых данных, пока старая система остаётся рабочей.
4. **Синхронизация данных.** Хотя синхронизация сложна, в нашем случае мы можем использовать подход **one‑way sync** (новая система получает копию данных из старой) и постепенно переходить к двухсторонней синхронизации на финальном этапе.
5. **Соответствие 152-ФЗ.** Параллельный запуск позволяет провести все необходимые проверки безопасности (шифрование, аудит) до того, как новые данные станут "живыми".

## 4. Ограничения и их преодоление

| Ограничение | Способ преодоления |
|-------------|---------------------|
| Двойные затраты на инфраструктуру | Использование облачных ресурсов по требованию, деплой в Kubernetes с автоскейлингом |
| Сложность синхронизации данных | Разработка ETL-пайплайна (Apache NiFi / Kafka) для односторонней синхронизации, затем – двухсторонней через CDC (Change Data Capture) |
| Двойной ввод данных сотрудниками | Автоматическая синхронизация, минимизация ручного ввода. На этапе параллельного запуска новая система используется для аналитики и отчётов, старая – для операций |
| Длительность перехода | Разбиение на этапы: сначала нечувствительные модули (запись), затем критичные (оплата, медицина) |

## 5. Итог

Выбранная стратегия **Parallel run** обеспечивает наилучший баланс между безопасностью, управляемостью и реализуемостью в условиях компании «Медикаменте». Она позволяет избежать катастрофических последствий неудачной миграции и даёт команде время на отладку и обучение.
