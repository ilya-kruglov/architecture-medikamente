# Управление рисками и распределение ролей

## 1. Матрица рисков (Top-10)

| # | Риск | Вероятность | Влияние | Стратегия | Мера снижения | Ответственный |
|---|------|-------------|---------|-----------|---------------|---------------|
| R1 | **Потеря данных при миграции** | Средняя | Критическое | Предотвращение | Полный бэкап перед каждым этапом, проверка целостности, двойная запись (журнал транзакций) | DBA / DevOps |

| R3 | **Простой системы (downtime)** | Низкая | Критическое | Предотвращение | Тщательное тестирование отказоустойчивости, резервный DNS, автоматический rollback-скрипт | DevOps |
| R4 | **Ошибки в работе нового интерфейса** | Высокая | Среднее | Обучение | Демо-сессии, создание видео-инструкций, чат-бот поддержки | Product Manager / Business Analyst |
| R5 | **Утечка данных (PII/Medical)** | Низкая | Критическое | Предотвращение | Шифрование на всех этапах, строгий ABAC, аудит всех операций | Security / DPO |
| R6 | **Нарушение сроков (затягивание)** | Средняя | Среднее | Управление | Более 5 рабочих дней задержки → эскалация к техдиректору; пересмотр объёма MVP | Project Manager |
| R7 | **Недостаток навыков у команды** | Высокая | Высокое | Обучение | Проведение workshops, привлечение внешнего консультанта по Kubernetes | Tech Lead / HR |
| R8 | **Проблемы с интеграцией 1С** | Высокая | Высокое | Тестирование | Разработка адаптера, тестирование на копии 1С, подготовка ручного обходного пути | Backend Dev / Business Analyst |
| R9 | **Нагрузка > ожидаемой** | Средняя | Высокое | Масштабирование | Автоскейлинг в K8s, горизонтальное масштабирование БД, CDN для статики | DevOps |
| R10 | **Отказ оборудования (сервер)** | Низкая | Критическое | Резервирование | Кластер K8s из 3+ нод, резервное электропитание, облачный бэкап | DevOps / IT-администратор |

## 2. План действий при инцидентах (Runbook)

| Инцидент | Действие | Ответственный | Время реакции |
|----------|----------|---------------|---------------|
| **Потеря соединения с БД** | 1. Проверить статус PostgreSQL. 2. Перезапустить pod. 3. Если не работает – поднять реплику | DevOps | 5 мин |
| **Обнаружение расхождения данных > 1%** | 1. Запустить детальный reconciliation-скрипт. 2. Выявить корневую причину. 3. Восстановить данные из бэкапа | Data Engineer | 1 час |
| **Массовые ошибки 5xx** | 1. Отключить новый сервис через Feature Flag. 2. Направить трафик на старую систему (read-only). 3. Анализ логов | Backend Dev | 10 мин |
| **Подозрение на утечку PII** | 1. Заблокировать доступ к данным. 2. Запустить аудит логов. 3. Уведомить DPO. 4. Оповестить регулятора (при необходимости) | Security / DPO | 15 мин |
| **Падение производительности** | 1. Увеличить количество реплик (kubectl scale). 2. Оптимизировать тяжёлые запросы. 3. Включить кеширование | DevOps | 30 мин |

## 3. Распределение ролей и ответственности

| Роль | Кто (из штата) | Ответственность на этапах миграции |
|------|---------------|-------------------------------------|
| **Project Manager (PM)** | Технический директор | Общее управление, синхронизация с бизнесом, утверждение этапов, коммуникация с руководством |
| **Tech Lead / Architect** | Технический директор (совмещает) | Принятие архитектурных решений, контроль качества кода, решение технических проблем |
| **DevOps Engineer** | Администратор сети (с дообучением) + новый найм | Инфраструктура (K8s, CI/CD, мониторинг, Vault), обеспечение отказоустойчивости, rollback |
| **Backend Developer** | 2–3 новых разработчика (Java) + Tech Lead | Разработка микросервисов, API, интеграции, исправление багов в процессе UAT |
| **Data Engineer / DBA** | Бизнес-аналитик (с дообучением Python/Spark) + внешний консультант | ETL, миграция данных, синхронизация, очистка данных, управление схемой БД |
| **Business Analyst** | Существующий бизнес-аналитик | Сбор требований, UAT, обучение пользователей, валидация данных, составление инструкций |
| **QA Engineer** | Новый найм или выделенный разработчик | Нагрузочное тестирование, регрессионное тестирование, автоматизация тестов (Playwright / JUnit) |
| **Security / DPO** | Технический директор (внешний консультант) | Аудит безопасности, проверка соответствия 152-ФЗ, управление доступом, реагирование на инциденты |
| **Business Stakeholders** | Главный врач, главный бухгалтер, руководитель ресепшена | Предоставление доступа к пользователям, обратная связь, принятие решения о переходе |

## 4. Критерии успешного завершения (Success Criteria)

| Критерий | Целевое значение | Способ проверки |
|----------|------------------|-----------------|
| Время простоя (downtime) | < 4 часа (в выходные) | Мониторинг uptime |
| Расхождение данных | < 0.01% (или 0 расхождений для финансов) | Reconciliation-скрипты |
| Время отклика API (p95) | < 200 мс | Prometheus / Grafana |
| Удовлетворённость пользователей | > 4.5 из 5 | Опрос после 2 недель работы |
| Инциденты безопасности | 0 | Аудит логов |
| Соответствие 152-ФЗ | 100% | Проверка DPO, внешний аудит |
