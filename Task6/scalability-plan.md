# План масштабирования системы классификации данных

## 1. Принципы масштабирования

| Принцип | Реализация |
|---------|------------|
| **Statelessness** | Все компоненты (кроме БД) не хранят состояние → горизонтальное масштабирование |
| **Asynchronous Processing** | Использование Kafka для асинхронной обработки → устойчивость к пиковым нагрузкам |
| **Partitioning** | Данные партиционируются по источнику или дате → параллельная обработка |
| **Auto-scaling** | Kubernetes HPA (Horizontal Pod Autoscaler) на основе CPU/Memory/Throughput |

## 2. Масштабирование по компонентам

| Компонент | Механизм масштабирования | Параметры автоскейлинга |
|-----------|---------------------------|-------------------------|
| **Ingestion (NiFi/Kafka)** | Увеличение числа партиций Kafka (до 100+), горизонтальный скейлинг consumer-групп | При backlog > 100 000 сообщений |
| **Schema Registry** | Репликация, кластеризация | Статично (малонагружен) |
| **Classification Engine** | Горизонтальное масштабирование Spark-воркеров (Kubernetes) | При CPU > 70% или Throughput < 5000 записей/мин |
| **DLP Scanner** | Отдельный пул подов (с GPU, если необходимо) | При загрузке очереди > 1000 файлов |
| **Policy Engine (OPA)** | Репликация + кеширование результатов | При latency > 100 мс |
| **Metadata Repository** | Вертикальное масштабирование (PostgreSQL) + Elasticsearch кластер | При размере индекса > 100 ГБ |
| **Zones (HDFS/MinIO/ClickHouse)** | Добавление нод в кластер, партиционирование таблиц | При заполнении > 80% |

## 4. Стратегия расширения

### 4.1. Горизонтальное масштабирование (Kubernetes)

```yaml
# Пример HPA для Classification Engine
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: classification-engine-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: classification-engine
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Pods
    pods:
      metric:
        name: kafka_consumer_lag
      target:
        type: AverageValue
        averageValue: 10000
```

### 4.2. Вертикальное масштабирование (для БД)

- **PostgreSQL:** увеличение размера инстанса, использование read-replicas для отчётов
- **ClickHouse:** добавление нод в кластер, шардирование по дате
- **Elasticsearch:** увеличение количества шардов, добавление нод data-hot/warm/cold

### 4.3. Кеширование

- Redis для кеширования результатов классификации (TTL = 1 час)
- Кеш политик OPA для снижения latency

### 4.4. Оптимизация данных

- Партиционирование по дате для быстрых запросов
- Архивация старых данных (> 1 года) в холодное хранилище (AWS Glacier / Azure Archive)
- Сжатие данных (Parquet, ZSTD)

## 5. Мониторинг масштабирования

| Метрика | Целевое значение | Действие |
|---------|------------------|----------|
| CPU Usage (средний) | < 60% | Увеличить реплики при превышении |
| Memory Usage | < 75% | Увеличить память или реплики |
| Kafka Consumer Lag | < 10 000 | Увеличить consumer-группы |
| Query Latency (ClickHouse) | p95 < 200 мс | Добавить индексы или шарды |
| Storage Usage | < 80% | Добавить ноды или архивировать |

## 7. План действий при достижении лимитов

| Триггер | Действие | Ответственный | Время реакции |
|---------|----------|---------------|---------------|
| Throughput > 80% от максимума | Добавить реплики, увеличить ресурсы | DevOps | 1 час |
| Storage > 80% | Архивировать данные, добавить ноды | DBA | 1 день |
| Model Drift (F1 < 0.90) | Переобучить модель на новых данных | Data Scientist | 1 неделя |
| Новый источник данных | Добавить в Ingestion, адаптировать классификатор | Data Engineer | 2 недели |
| Новый тип ПДн/PII | Обновить паттерны, переобучить NER | Security / DS | 3 дня |
