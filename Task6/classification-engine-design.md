# Детальный дизайн движка классификации данных

## 1. Общая архитектура

Движок классификации данных является центральным компонентом аналитического хранилища (Data Lake) компании «Медикаменте». Он обеспечивает автоматическое обнаружение, классификацию и тегирование данных перед их загрузкой в хранилище, что позволяет:

- Соблюдать требования 152-ФЗ и Privacy by Design
- Разграничивать доступ на основе тегов (ABAC)
- Проводить аудит операций с чувствительными данными
- Обеспечивать качество данных для аналитики и ML

## 2. Компоненты движка

### 2.1. Ingestion Layer (Apache NiFi / Kafka)

**Назначение:** приём данных из различных источников с гарантией доставки.

- Поддерживаемые источники:
  - Легаси-системы: Excel-файлы (SMB/NFS), 1С (выгрузка CSV), файловый сервер
  - Операционная БД: CDC через Debezium → Kafka
  - Внешние партнёры: REST API, SFTP, email (парсинг)
  - Лаборатория: API с mTLS
- Механизмы:
  - Буферизация (Kafka с retention 7 дней)
  - Обработка ошибок (DLQ — Dead Letter Queue)
  - Мониторинг lag-ов

### 2.2. Schema Registry (Confluent Schema Registry / Avro)

**Назначение:** управление схемами данных для обеспечения совместимости при структурных изменениях.

- Поддерживает эволюцию схем (backward/forward compatibility)
- Хранит версии схем с историей изменений
- Интегрируется с Classification Engine для валидации полей

### 2.3. Classification Engine (Python / Apache Spark)

**Назначение:** основной компонент, выполняющий классификацию данных.

**Процесс классификации:**
1. Получение данных из Ingestion Layer
2. Извлечение содержимого:
    - Для структурированных данных → чтение полей
    - Для текстовых файлов → NLP-анализ
    - Для сканов/изображений → OCR (Tesseract)
3. Обнаружение ПДн/PII:
    - Regex-паттерны: телефон, email, СНИЛС, паспорт
    - ML-модели: NER (Named Entity Recognition) на основе spaCy / BERT
    - Кастомные правила для медицинских терминов
4. Применение правил классификации:
    - Если найдено ФИО, телефон, адрес → PII_SENSITIVE
    - Если найдено название болезни, диагноз → MEDICAL
    - Если найдена сумма, номер карты → FINANCIAL
    - Иначе → OPERATIONAL или PUBLIC
5. Применение политик (OPA):
    - Проверка, какие действия разрешены с данными данного класса
    - Определение, нужно ли маскирование или полное обезличивание
6. Сохранение тегов в Metadata Repository
7. Маршрутизация в соответствующую зону хранилища

### 2.4. DLP Scanner (Custom ML + NLP + OCR)

**Назначение:** глубокий анализ неструктурированных данных (PDF, JPG, DOCX).

- **NLP-модели:** для анализа текста (выявление медицинских терминов, диагнозов)
- **OCR:** для извлечения текста из сканов (Tesseract / Azure Cognitive Services)
- **Распознавание лиц:** (опционально) для проверки, что на скане нет фото пациента
- **Интеграция:** вызывается Classification Engine для сложных случаев

### 2.5. Policy Engine (Open Policy Agent — OPA)

**Назначение:** централизованное применение политик доступа и обработки.

Пример политики:

```rego
package data_classification

default allow = false

allow {
    input.sensitivity == "PII_SENSITIVE"
    input.action == "mask"
}

allow {
    input.sensitivity == "MEDICAL"
    input.action == "encrypt"
}

allow {
    input.sensitivity == "PUBLIC"
    input.action == "store"
}
```

### 2.6. Metadata Repository (Apache Atlas / OpenMetadata)

**Назначение:** хранение всех метаданных: тегов, классификаций, lineage, политик.

Хранит:

- Теги для каждой записи/файла
- Историю классификаций
- Data lineage (откуда пришли данные, какие трансформации прошли)
- Политики доступа

## 3. Зоны хранилища (Data Lake)

| Зона | Назначение | Содержимое | Доступ | Retention |
|------|------------|------------|--------|-----------|
| **Raw Zone** | Временное хранение исходных данных | Сырые данные в исходном формате (CSV, JSON, PDF, JPG) | Только ETL-пайплайны | 7 дней |
| **Staging Zone** | Данные после классификации | Данные с тегами, но без трансформации | ETL, Data Engineers (ограниченно) | 30 дней |
| **Classified Zone** | Данные с применёнными политиками | ПДн/PII замаскированы, Medical зашифрованы, теги применены | Только авторизованные (ABAC) | По политикам (5–25 лет) |
| **Analytics Zone** | Обезличенные данные для BI/ML | Агрегаты, фичи, обезличенные таблицы | Аналитики, DS (полный доступ) | Бессрочно (обезличенные) |

## 4. Поток данных (пример)

1. **Вход:** Excel-файл с журналом записей (ФИО, телефон, диагноз, дата)
2. **Ingestion:** файл загружается через NiFi, сохраняется в Raw Zone
3. **Classification Engine:**
   - Извлекает данные (pandas)
   - Применяет regex: находит ФИО (PII_SENSITIVE), телефон (PII_SENSITIVE), диагноз (MEDICAL)
   - Тегирует каждую колонку
   - Сохраняет теги в Apache Atlas
4. **DLP Scanner:** (опционально) если есть вложенные комментарии, проверяет их через NLP
5. **Policy Engine:** определяет, что PII_SENSITIVE нужно маскировать, MEDICAL — шифровать
6. **Staging Zone:** данные сохраняются с тегами
7. **Transformation (Spark job):**
   - Маскирует ФИО → И\*\*\*\*\*в
   - Шифрует диагноз (AES-256)
8. **Classified Zone:** сохранение замаскированных данных
9. **Analytics Zone:** агрегация (количество записей по дням без ПДн/PII)
10. **Аналитик** строит отчёт по Analytics Zone
